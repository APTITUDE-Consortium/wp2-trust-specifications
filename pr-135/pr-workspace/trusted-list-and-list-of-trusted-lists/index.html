    Trusted list and list of trusted lists

    This section describes the format and contents of the LoTE and how it is used to provide Trust Anchors within APTITUDE.

    The LoTE is a compilation of the information submitted by Member States about the following entities:

    1. PID Providers;
    2. Wallet Providers;
    3. Providers of WRPAC;
    4. PuB-EAA Providers;
    5. Registrars and Registers.

    In the context of the EUDI Wallet, the EC will publish the related LoTE on the eIDAS Dashboard, which will be accessible at https://eidas.ec.europa.eu/efda/wallet.

    The LoTE follows the same structure defined for Trusted Lists on [ETSI TS 119 612]. A LoTE, however, supports both the JSON and XML formats, as defined in [ETSI TS 119 602].

    All LoTE SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1] for JSON-formatted LoTE, and with XML Advanced Electronic Signatures (XAdES) Baseline B signature, as defined in [ETSI EN 319 132-1] for XML-formatted LoTE.

    APTITUDE Implementation Choices

    • Only the LoTE SHALL be used; Trusted Lists and LOTL SHALL NOT be used.
    • QEAA Providers and EAA Providers SHALL have a dedicated LoTE.
    • Each LoTE type SHALL be published at a distinct endpoint. A LoTE consumer SHALL use the endpoint published for the required LoTE type and SHALL NOT infer the endpoint of one LoTE type from that of another.
    • The Official Journal of APTITUDE (OJA) SHALL publish a fixed location and fixed authorized signing certificate set for each LoTE type. The publication URI, type-specific locations, and certificate sets SHALL remain unchanged during the pilot.
    • APTITUDE entities MAY cache an accepted LoTE. A cached list SHALL be refreshed no later than 24 hours after its retrieval or its NextUpdate value, whichever occurs first. If the required refresh fails, the cached list SHALL NOT be used for a trust decision.
    • The highest accepted LoTESequenceNumber and a SHA-256 digest of the accepted signed list content for each type SHALL be retained across refreshes and restarts.

    APTITUDE Pilot OJA Publication

    The OJA publication SHALL remain at a fixed URI for the duration of the pilot. It is not signed or independently authenticated. LoTE consumers accept its type-specific locations and signing certificate sets as pilot discovery data. A successful comparison with that certificate set does not independently authenticate the OJA publication.

    Data Models¶

    This section specifies the profiles and formats that the various LoTE within the APTITUDE ecosystem SHALL utilize, depending on their specific use cases.

    The following repository provides the base normative JSON and XML schemas required for implementing the LoTE: https://forge.etsi.org/rep/esi/x19_60201_lists_of_trusted_entities.

    The LoTE OpenAPI description documents the pilot's type-specific retrieval endpoints and the JSON LoTE carried in a signed compact JWT. Its paths and example values are illustrative; the actual fixed endpoint and authorized signing certificates for each type are published by the OJA. The OpenAPI document covers the JSON representation; optional XML support for QEAA Provider Lists is described below.

    APTITUDE Implementation Choice

    The following formats SHALL be used for the different types of lists:

    • PuB-EAA Provider Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • Wallet Provider Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • Provider of WRPAC Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • Provider of WRPRC Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • Registrar and Register Provider Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • PID Provider Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    • During the pilot, QEAA Provider Lists SHALL be published in JSON format and signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1]. Implementations MAY additionally support XML-formatted QEAA Provider Lists signed with XML Advanced Electronic Signatures (XAdES) Baseline B signature, as defined in [ETSI EN 319 132-1]. XML support SHALL NOT be required for pilot interoperability.
    • EAA Provider Lists are published in JSON format, and SHALL be signed with Compact JAdES Baseline B signature, as defined in [ETSI TS 119 182-1].
    Compact JAdES Baseline B Signature Profile¶

    APTITUDE Implementation Choice

    The use of a JWT representation for a JSON-formatted LoTE and the selection of x5t#S256 as the certificate-binding parameter are implementation choices. The JWT Claims Set SHALL contain the LoTE object as the private LoTE claim.

    For a JSON-formatted LoTE, the Compact JAdES Baseline B signature SHALL be used, its protected JOSE header SHALL satisfy [ETSI TS 119 182-1, Clauses 5.1 and 6.3]:

    Parameter Presence Requirement
    alg REQUIRED SHALL be ES256.
    iat REQUIRED Specifies the claimed signing time.
    x5t#S256 REQUIRED Contains the Base64url-encoded SHA-256 thumbprint of the DER encoding of the authorized signing certificate in the type-specific OJA certificate set.

    The x5c, kid, and x5u header parameters SHALL NOT be used in the pilot profile. A validator SHALL select the signing certificate only from the type-specific OJA certificate set, using x5t#S256.

    XAdES Baseline B Signature Profile¶

    Note

    This section therefore uses [ETSI EN 319 132-1] as the normative reference for the requested Baseline B profile.

    For an XML-formatted LoTE, the XAdES Baseline B signature SHALL be an enveloped XML signature. The following requirements apply in addition to the XML LoTE schema and the requirements in [ETSI TS 119 602, Clauses 6.8.0 and 6.8.1]:

    Component Presence Requirement
    ds:Signature REQUIRED The signature SHALL be a child of the XML ListOfTrustedEntities document element.
    Document reference REQUIRED A ds:Reference with URI="" SHALL reference the LoTE document and SHALL use the enveloped-signature transform followed by exclusive XML canonicalization.
    ds:CanonicalizationMethod REQUIRED The ds:SignedInfo/ds:CanonicalizationMethod SHALL identify exclusive XML canonicalization.
    ds:KeyInfo/ds:X509Data/ds:X509Certificate REQUIRED The signing certificate SHALL be present. It SHALL be the certificate used to verify ds:SignatureValue.
    xades:QualifyingProperties REQUIRED Exactly one xades:QualifyingProperties element SHALL be directly incorporated in one ds:Object, and its Target SHALL reference the ds:Signature identifier.
    xades:SignedProperties reference REQUIRED A ds:Reference SHALL reference xades:SignedProperties with Type="http://uri.etsi.org/01903#SignedProperties".
    xades:SigningTime REQUIRED Exactly one xades:SigningTime SHALL be present in xades:SignedSignatureProperties and SHALL express the claimed signing time in UTC.
    xades:SigningCertificateV2 REQUIRED Exactly one xades:SigningCertificateV2 SHALL be present. Its first xades:Cert SHALL identify the signing certificate through a digest of that certificate's DER encoding.
    xades:DataObjectFormat REQUIRED One xades:DataObjectFormat SHALL describe the signed LoTE document, excluding xades:SignedProperties, and SHALL contain its MIME type.

    For XML-formatted LoTE, the signature method SHALL use ECDSA with SHA-256 and a P-256 signing key. The digest methods for the document and signed-properties references SHALL use SHA-256.

    APTITUDE Implementation Choice

    The digest in xades:SigningCertificateV2/xades:Cert/xades:CertDigest SHALL use SHA-256 and its ds:DigestValue SHALL be the standard XML Signature Base64 encoding of the digest of the signing certificate's DER encoding. IssuerSerialV2 SHALL NOT be used as the certificate binding, and the xades:Cert/@URI SHALL be omitted.

    The xades:SigningTime value is a claimed signing time and SHALL NOT be treated as a trusted timestamp.

    The certificate in ds:KeyInfo SHALL be identified by the first xades:SigningCertificateV2/xades:Cert through the digest of its DER encoding. The verifier SHALL compare that certificate by exact DER identity with the type-specific set supplied by the OJA, as specified in the LoTE validation process. A valid XAdES signature alone does not establish consistency with that set.

    APTITUDE Pilot History and Publication

    • The pilot SHALL publish only the current LoTE version for each type at its fixed endpoint.

    • For types other than PuB-EAA Provider, the current list SHALL NOT contain historical service information, and the LoTE Provider SHALL NOT publish earlier instances for historical membership validation.

    These pilot choices depart from the archive retrieval URI and self-pointer requirements for the corresponding profiles in [ETSI TS 119 602, Annexes D-G and I]. The PuB-EAA Provider LoTE SHALL retain its required ServiceHistory in the current list.

    APTITUDE Implementation Choices

    The Trust Anchors for the Issuance and Revocation services SHALL be the same, and SHALL be listed in the ServiceDigitalIdentity component of the ServiceInformation component.

    For the ETSI-profiled list types other than Registrar, the ServiceTypeIdentifier SHALL be formed as a URI string http://uri.etsi.org/19602/SvcType/{Specific_attestation}/Issuance or http://uri.etsi.org/19602/SvcType/{Specific_attestation}/Revocation. The {specific_attestation} fragment SHALL be valued as:

    • PID for PID Providers Trust Anchors;
    • WalletSolution for Wallet Providers' owned Wallet Solution Trust Anchors;
    • WRPAC for Providers of WRPAC's Trust Anchors;
    • WRPRC for Provider of WRPRC's Trust Anchors;
    • PubEAA for Pub-EAA Providers' Trust Anchors.

    For the pilot-specific QEAA Provider and EAA Provider lists, ServiceTypeIdentifier SHALL respectively use http://aptitude-consortium/SvcType/{Specific_attestation}/Issuance, http://aptitude-consortium/SvcType/{Specific_attestation}/Revocation as applicable.

    For the Registrar LoTE type, the ServiceTypeIdentifier SHALL be formed as a URI string http://uri.etsi.org/19602/SvcType/Register.
